## 2. Voice — this was the real problem

You said voice is still the weak point. It is, and the cause is concrete.

### Fixed: the stream could silently swallow commands

`deepgram-stream.ts` emitted a command **only** on `speech_final`, using only _that
message's_ transcript. Two bugs in one line:

1. **Dropped words.** A sentence arrives as several `is_final` segments and only the
   last carries `speech_final`. "Kali, avanzo tres casilleros" reached the LLM as
   "tres casilleros" — the wake word and the verb gone.
2. **Never firing at all.** `speech_final` comes from a VAD watching for _silence_.
   Kids around a table plus your looping habitat ambience keep that VAD hot, so in the
   exact conditions Kali is built for, it can simply never fire and the command is
   never delivered.

Now the stream accumulates `is_final` segments and flushes on whichever end-of-speech
signal arrives first — `speech_final`, or Deepgram's `UtteranceEnd`, which watches
word-timing gaps instead of raw audio and is immune to background noise. Deepgram
documents using both together for exactly this reason. Added `utterance_end_ms=1000`
(tunable via `VITE_STT_UTTERANCE_END_MS`) and 5 tests covering both paths.

### Fixed: the mic un-muted mid-setup (E3)

Regression from the in-flight Deepgram work — `handleWakeWord()` was deleted but its
paired release was left in `handleTranscription`'s `finally`. After the first player's
name, ambient capture unmuted and Kali's own TTS fed back into the open stream for the
rest of setup. The old test asserted the buggy behavior; it now asserts the invariant.

### Fixed: wake word via `keyterm`

You had 8 spellings (`kali`, `cali`, `calli`, `kaly`, `caly`, `callie`, `callee`,
`kari`) and a hand-rolled Levenshtein matcher, all correcting the recogniser _after_ it
guessed wrong. Nova-3 supports `keyterm`, which biases it toward the right word up
front. A rejected query param kills the whole socket and no unit test can catch that, so
**I verified it against the live streaming websocket**, not just REST: the real query
string (`model=nova-3&language=es&…&utterance_end_ms=1000&keyterm=kali`) opens cleanly,
while a control with a bogus `model` fails to open at all — so the check discriminates.
The 8-spelling list is still there as a safety net; drop entries once you see real
transcripts.

### Still open: three overlapping gates

The deeper issue is architectural. You have **three** mechanisms deciding whether speech
is a command, each added to patch the previous one rather than replace it:

1. wake-word matching (the fuzzy list)
2. `listeningMode` + a 10s `openPromptedWindow()` timer
3. `intent-router`'s regex heuristics — then an **LLM** `analyzeResponse` fallback

`isLikelyStructuredAnswer` fires on any bare digit, so "he's 7 years old" is a game
command. Meanwhile the LLM is _already_ in the loop interpreting every transcript.

**The ponytail move is to delete the regex layer.** Keep the wake word (cheap, keyterm
does the work now) and the LLM (already paying for it); drop the middle tier that
guesses with regexes at what the LLM decides properly one call later. That collapses
three gates to two and removes the layer that produces the most surprising misfires.
I did not do this — it touches `intent-router.ts`, which is part of your uncommitted
work, and it's a behavioural change that deserves your call rather than my guess.

## 3. API keys — `worker/`

Deepgram's `POST /v1/auth/grant` mints a **short-lived JWT** (default 30s, max 1h). The
token only has to be valid for the websocket _handshake_; the stream then stays open on
its own. So the browser never needs the real key, and **the Worker never proxies the
websocket** — no `WebSocketPair`, no streaming audio through Cloudflare, no added
latency on the audio path. That is a much smaller thing to build than it first looks.

`worker/index.ts` (~110 lines, fetch-only):

- `POST /api/deepgram-token` → mints a 60s JWT, returns `{access_token, expires_in}`
- `POST /api/llm` → pass-through to DeepInfra with the real key attached
- Origin-checked against `ALLOWED_ORIGIN`, or anyone can spend your credits through it

### Deploying

```bash
cd worker
# set ALLOWED_ORIGIN in wrangler.toml to your real app origin first
wrangler secret put DEEPGRAM_API_KEY
wrangler secret put DEEPINFRA_API_KEY
wrangler deploy
```

### Then, and only then, the client change

**I deliberately did not make this change** — it breaks the app until the Worker is
live. Two edits:

1. `deepgram-stream.ts` — fetch a token, then connect with it. Note the JWT is long
   enough to blow the `Sec-WebSocket-Protocol` header limit, so pass it as a query
   param rather than a subprotocol:

   ```ts
   const { access_token } = await (
     await fetch(`${CONFIG.KEY_BROKER_URL}/api/deepgram-token`, { method: "POST" })
   ).json();
   url.searchParams.set("access_token", access_token);
   this.ws = new WebSocket(url.toString()); // no subprotocol array
   ```

2. `DeepInfraClient.makeApiCall` — point at `${CONFIG.KEY_BROKER_URL}/api/llm` and drop
   the `Authorization` header.

Then delete `DEEPGRAM.API_KEY` / `DEEPINFRA.API_KEY` from `config.ts` and the `VITE_*`
keys from `.env` and Vercel. **Rotate both keys** — the current ones have been shipped
in the bundle and must be treated as public.
