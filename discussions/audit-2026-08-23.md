## 1. Errors

### E1 `[HEAD]` — Production downloads a ~40MB Vosk model that nothing reads

`src/main.ts:17` fires `ModelManager.getInstance().getModel()` at module load,
then immediately `URL.revokeObjectURL`s the result. The comment above it
("Vosk stays the wake-word gate even when Deepgram is selected") is **false** —
`kali-app-core.ts:366` hard-imports `DeepgramStream`.

Proof from `dist/`:

- `vosk-browser` → **not in the bundle**
- `WakeWordDetector` → **not in the bundle**
- `kali-models-v1` + `https://ygs8n4tcvald8mq6.public.blob.vercel-storage.com/vosk-model-small-es-0.42.zip` → **in the bundle**, reachable from the `main` entry

Every first-time visitor pays a 40MB download into Cache Storage for a model no
code path consumes. Cached after first load, but it is 40MB of a kid's data plan,
a cold-start stall, and Vercel Blob egress — for nothing.

The fix is three places, not one:

1. `main.ts:15-19` — delete the preload.
2. `vite.config.ts:52-58` — a `runtimeCaching` `CacheFirst` rule for
   `^https://alphacephei\.com/vosk/models/.*`. Note this rule is _already_ broken:
   the real URL is the Vercel Blob host, so the pattern never matched anything.
3. `vite.config.ts:129` — `manualChunks: if (id.includes("vosk-browser")) return "vosk"`,
   a chunk rule for a dependency that is never imported.

That also strips `vosk-browser`, the app's **only** production dependency.

### E2 `[HEAD]` — Both API keys ship inside the JavaScript bundle

`VITE_DEEPGRAM_API_KEY` and `VITE_DEEPINFRA_API_KEY` are inlined into
`dist/assets/debug-CwTqQFT1.js` — confirmed by grepping the built file for the
literal key values from `.env`. Anyone who loads the deployed page can read both
and spend your credits. `VITE_*` means "public" by definition.

If the deploy URL is private this is low-grade. If it is public, this is the most
expensive line in the repo. Real fix is a small serverless proxy (Vercel function)
holding the keys; short-term, rotate them and set spend caps.

### E3 `[in-flight]` — Ambient mic un-mutes after the first name during setup

**This is a regression in your uncommitted work, not a shipped bug.** At `HEAD`
the refcount was balanced: `handleWakeWord()` acquired a hold per utterance
(`HEAD:532`) and `handleTranscription`'s `finally` released it per utterance.

The Deepgram migration deleted `handleWakeWord()` — correctly, since a continuous
stream has no wake-word event — but **left the per-utterance release in place**.
The only remaining acquire is `NameCollector`'s single long-lived hold
(`kali-app-core.ts:527`, via `name-collector.ts:51`).

Result: player 1 says their name → `finally` drops the hold 1→0 → ambient capture
unmutes → the rest of setup runs unmuted, with Kali's own TTS feeding back into
the open Deepgram stream.

Fix: **delete** the `finally { this.releaseAmbientCaptureMute(); }` at
`kali-app-core.ts:723`. Don't relocate it — gameplay never acquires, so in the
gameplay branch it was always a no-op. Let `cleanupNameCollection` own the whole
lifecycle, which it already does.

## 3. The structural note

The README promises "a **game-agnostic engine** capable of learning new games…
simply by being fed their rulebooks". The engine currently contains **169
Kalimba-specific references across 15 files** that are supposed to be
game-agnostic (counting only named game nouns — `kalimba`, `torch`, `wasp`,
`magicDoor`, `oceanForest`, `skull` — not bare numbers):

| file                               | hits |
| ---------------------------------- | ---- |
| `board-effects-handler.ts`         | 81   |
| `narration-policy.ts`              | 16   |
| `execute-player-rolled.ts`         | 15   |
| `types.ts`                         | 10   |
| `board-effects-movement-policy.ts` | 10   |
| _(10 more)_                        | 37   |

`isKalimbaOceanForestPortal82Hop`, `consumeOceanForestPortal82Penalty`,
`applyCheckTorchEffect`, `applyCheckAntiWaspEffect` — torches and wasps are
Kalimba nouns living in engine code. `board-effects-handler.ts` is one class with
**49 methods** in 1106 lines.

This is the actual shape of the codebase: the _ceremony_ of a game-agnostic engine
(7 policy/enforcer/inference modules, an 8-file validator split, a provider
interface with no implementations, an abstract base class with one child) wrapped
around what is really a hardcoded Kalimba implementation. The abstraction layers
cost real lines but don't deliver the genericity they're named for — a second game
would still require editing the engine.

Two coherent options, and picking one is worth more than any single fix above:

1. **Admit it's a Kalimba app.** Delete the policy-module ceremony, inline the
   single-caller layers, keep one honest readable board-effects module. Fastest
   path, smallest codebase.
2. **Actually go generic.** Push the 169 hardcoded references into
   `public/games/kalimba/config.json` (which already carries flags like
   `oceanForestOneShotPortal`). Then the layers earn their keep.

Doing neither costs the most — you pay the abstraction tax without getting the
abstraction.
